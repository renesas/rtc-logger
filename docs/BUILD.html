Windows — Install Order

All installers require Administrator mode except pip install which runs as a normal user once Python is installed.

1. MSVC Build Tools Required by clang-cl for Windows headers and the linker. Download: https://visualstudio.microsoft.com/downloads/ Scroll to “Build Tools for Visual Studio” and install: - Desktop development with C++ - MSVC toolchain - Windows SDK (latest)

2. LLVM generic Used for host unit tests (clang-cl, x86_64-pc-windows-msvc target). Download: https://releases.llvm.org/ Install to the default path C:\Program Files\LLVM.

3. e2studio with ATfE toolchain The e2studio FSP bundle includes ATfE (Arm Toolchain for Embedded, LLVM variant) which provides clang.exe targeting arm-none-eabi with the correct bare-metal sysroot headers (setjmp.h, string.h, etc.) for Cortex-M33 firmware cross builds. Download: https://www.renesas.com/en/software-tool/e2studio Remember the Default install path (for example) : C:\Users\<username>\AppData\Local\Programs\Renesas\RA\e2studio_v*_fsp_v6.5.0\

ATfE clang.exe is at: ...\toolchains\llvm_arm\ATfE-21.1.1-Windows-x86_64\bin\clang.exe

PATH order matters: Generic LLVM must appear after ATfE in env.ps1 so that clang-cl.exe resolves to the generic LLVM (x86_64-pc-windows-msvc) and clang.exe resolves to ATfE (arm-none-eabi). See scripts/env.ps1 for the correct order.

4. Python 3 Required to run Meson, Ninja, and the RASC helper scripts. Download: https://www.python.org/downloads/windows/ During install tick “Add Python to PATH”.

Then install Meson and Ninja (no admin needed):

This is separate from e2studio — e2studioc.exe bundled with e2studio cannot run --generate headlessly (it waits for an Eclipse socket connection). The standalone installer is required.

⚙️ Example Project Mode vs. Expert Mode

The PES supports two operating modes selected at build time by RS_RTC_LOGGER_CFG_EXAMPLE_MODE_ENABLE in rs_rtc_logger_cfg.h.

Mode Value Description
Example Project 1 (default) PES auto-manages Open()/Start(); owns an internal FreeRTOS consumer task
Expert 0 Application owns the full lifecycle: Open() → Start() → EventTrigger() → Write() → Stop() → Close()

The default in rs_rtc_logger_cfg.h is 1 (Example Project mode). This is the correct production setting and is used by both firmware builds and host unit tests without any override.

To switch the host unit tests to Expert mode, add '-DRS_RTC_LOGGER_CFG_EXAMPLE_MODE_ENABLE=0' to the c_args line in meson/llvm-clangcl-msvc.ini. Do not change rs_rtc_logger_cfg.h itself.

✅ Host Unit Tests

The host test build uses two isolation macros set globally in meson/llvm-clangcl-msvc.ini:

  • RS_RTC_LOGGER_TEST_HOST_BUILD=1 — redirects rs_rtc_logger_types.h to use tests/stubs/ headers instead of FSP and FreeRTOS headers
  • RS_RTC_LOGGER_CFG_EXAMPLE_MODE_ENABLE — not overridden; defaults to 1 (Example Project mode), matching the firmware

rs_rtc_logger_hal.c is excluded from the host build. Mock implementations in test_rs_rtc_logger_core.c satisfy all HAL symbols at link time.

🎯 Firmware build outputs explained

Each firmware build produces two independent SREC images. Flash one or the other depending on what you want to run on the board.

rtc_event_logger_on_<board>_clang.srec — Application firmware The full RTC Event Logger demo. Runs the FreeRTOS blinky thread, initialises the RTC and UART via FSP drivers, and executes the rs_rtc_logger_demo example. Flash this for normal operation or demonstration.

rtc_event_logger_unittest_on_<board>_clang.srec — On-target Unity tests A separate firmware image that replaces main.c and blinky_thread_entry with a Unity test runner. On boot it runs the test_rs_rtc_logger_format and test_rs_rtc_logger_core test suites directly on the Cortex-M33 using the real FSP RTC and UART drivers, then streams Unity pass/fail output over UART. Flash this to verify the rs_rtc_logger library on real silicon.

TDD workflow

1. meson test -C build-clangcl        # host tests: fast, no hardware
2. flash unittest SREC → read UART    # on-target tests: real drivers, real silicon
3. flash app SREC                     # demo / production firmware

✅ Flash Programming (rfp-cli)

J-Link reset behaviour and RTC — important

The RA4E2 and RA6E2 RTC uses a 32.768 kHz sub-clock oscillator that is sensitive to how the MCU is reset after programming. There are two reset modes in rfp-cli:

  • -reset (default): Issues a J-Link system reset command via SWD. This pulses the reset line and reinitialises the debug interface. The system reset stops the sub-clock oscillator, leaving the RTC counter frozen after startup. Timestamps stop incrementing — all events log the same second regardless of how much time has passed.

  • -run: Simply releases the nRESET pin after programming without issuing a J-Link system reset command. The MCU starts from the natural power-on reset state that occurred during chip erase. The sub-clock oscillator is not disturbed and the RTC counts correctly.

This project uses -auto -run on all rfp_program and rfp_program_ut targets. After flashing completes the board starts automatically via pin release. No manual reset button press is required.

e2studio debugger: The same issue occurs when downloading firmware via the e2studio debugger. See the section below for how to configure e2studio to use pin-release reset instead of system reset.

Program application firmware

meson compile -C build-ra4e2 rfp_program   # RA4E2
meson compile -C build-ra6e2 rfp_program   # RA6E2

Program Unity test firmware

meson compile -C build-ra4e2 rfp_program_ut
meson compile -C build-ra6e2 rfp_program_ut

🔌 e2studio debugger — reset configuration for RTC

The same J-Link system reset issue that affects rfp-cli also affects the e2studio debugger. When you click Debug or Download and Debug, e2studio performs a system reset via J-Link after programming which freezes the RTC counter for the same reason described above.

Root cause — three keys in the .launch file

The .launch file (XML) in the e2studio project root contains three settings that together cause a J-Link system reset after every download:

<!-- line ~56: reset the target after downloading firmware -->
<booleanAttribute key="com.renesas.hardwaredebug.arm.jlink.connection.resetAfterDownload" value="true"/>

<!-- line ~87: reset the target after reloading -->
<booleanAttribute key="com.renesas.hardwaredebug.arm.jlink.options.ArmJLinkDebugToolSettingsTree.resetAfterReload" value="true"/>

<!-- inside serverParam string: server-side reset-on-reload flag -->
-uresetOnReload= 1

Fix option A — edit the .launch file directly (recommended)

  1. Close e2studio (or at least close the debug session).
  2. Open the .launch file in a text editor — it is in the project root, named after the debug configuration (e.g. RTC_Event_Logger_FPB_RA4E2_Debug_Flat.launch).
  3. Make these three changes:
<!-- change value="true" to value="false" -->
<booleanAttribute key="com.renesas.hardwaredebug.arm.jlink.connection.resetAfterDownload" value="false"/>

<!-- change value="true" to value="false" -->
<booleanAttribute key="com.renesas.hardwaredebug.arm.jlink.options.ArmJLinkDebugToolSettingsTree.resetAfterReload" value="false"/>

<!-- inside the serverParam string, change 1 to 0 -->
-uresetOnReload= 0
  1. Save the file and reopen e2studio. The new values take effect immediately.

Fix option B — e2studio GUI

  1. Open Run → Debug Configurations
  2. Select your project’s debug configuration
  3. Go to the Debugger tab → Connection Settings sub-tab
  4. Uncheck “Reset after download” (maps to resetAfterDownload)
  5. Go to the Debugger tab → Debug Tool Settings sub-tab
  6. Uncheck “Reset after reload” (maps to resetAfterReload)
  7. Click Apply then Close

Note: The .launch file stores all debug configuration settings. Commit it to the repo so all developers get the correct reset behaviour automatically. The fix must be applied to both the RA4E2 and RA6E2 debug configurations.

FSP v6.5.0 migration — deviations from e2studio example projects

This section documents every structural difference discovered when migrating the e2studio example projects (RTC_Event_Logger_FPB_RA4E2_v15 and RTC_Event_Logger_FPB_RA6E2_v18) to FSP v6.5.0 with the Meson build system. It exists so that future changes to the e2studio reference projects can be compared against this list to identify what needs updating here.

1. hal_entry.c no longer generated by RASC

e2studio reference project (FSP v6.4.0): RASC generated hal_entry.c into ra_gen/ as a thin wrapper calling g_hal_init() and starting the FreeRTOS scheduler.

FSP v6.5.0 behaviour: RASC no longer generates hal_entry.c. The function is declared in ra_gen/hal_data.h and must be provided by the application.

This project’s fix: src/hal_entry.c was added to the project source tree. It provides an empty hal_entry() body — the generated main.c calls g_hal_init() and vTaskStartScheduler() directly, so hal_entry() is an application hook that does nothing for this project.

2. hal_warmstart.c is now RASC-generated

e2studio reference project (FSP v6.4.0): hal_warmstart.c was a project source file in src/, hand-edited by the developer.

FSP v6.5.0 behaviour: RASC now generates hal_warmstart.c into the project directory (src/hal_warmstart.c inside the RASC projectdir). The content matches the original project version.

This project’s fix: src/hal_warmstart.c is no longer compiled from the project src/ tree. The RASC-generated copy is compiled instead (it is copied to firmware/generated/hal_warmstart.c by run_rasc.py). Including both would cause a duplicate R_BSP_WarmStart symbol at link time.

3. blinky_thread.c is a new RASC-generated file

e2studio reference project (FSP v6.4.0): No blinky_thread.c was generated by RASC. The FreeRTOS thread was registered manually.

FSP v6.5.0 behaviour: RASC generates ra_gen/blinky_thread.c and ra_gen/blinky_thread.h. blinky_thread.c defines blinky_thread_create() which is called by the generated main.c. Without it the firmware fails to link with undefined symbol: blinky_thread_create.

This project’s fix: blinky_thread.c is copied from the RASC projectdir (ra_gen/blinky_thread.c) to firmware/generated/blinky_thread.c by run_rasc.py and declared as a custom_target output so Meson compiles it.

4. FreeRTOS kernel sources ship in the RASC projectdir, not the FSP git repo

e2studio reference project: FreeRTOS kernel .c files were compiled from the FSP git repo at ra/aws/FreeRTOS/FreeRTOS/Source/. The FSP git tag v6.4.0 included them.

FSP v6.5.0 behaviour: The FSP v6.5.0 git repo (github.com/renesas/fsp) no longer includes FreeRTOS source files. Instead, RASC copies them from the RASC installer bundle into the --projectdir at ra/aws/FreeRTOS/FreeRTOS/Source/ when --generate is run headlessly.

This project’s fix: run_rasc.py copies the six FreeRTOS kernel .c files (tasks.c, queue.c, list.c, timers.c, event_groups.c, stream_buffer.c) from the RASC projectdir to firmware/generated/ with renamed filenames (ra_freertos_tasks.c etc.) so they can be declared as custom_target outputs and compiled by Meson without triggering setup-time path validation.

5. rm_comms_lock and rm_comms_uart removed from FSP src/

e2studio reference project (FSP v6.4.0): rm_comms_lock.c and rm_comms_uart.c existed under ra/fsp/src/ and were compiled as part of the FSP middleware layer.

FSP v6.5.0 behaviour: These source files were removed from src/. The rm_comms_lock.h stub in src/rm_comms_lock/ now contains a #error directive instructing users to use the inc/instances/ version instead. Attempting to compile rm_comms_lock.c produces a hard error.

This project’s fix: Both files are commented out in subprojects/packagefiles/fsp/meson.build with a version note.

6. picolibc linker script conflict with FSP linker script

e2studio reference project: e2studio links with a custom GCC or LLVM invocation that does not use the picolibc sysroot at link time.

This project’s issue: The ATfE toolchain’s --sysroot flag, when passed to the linker, causes ld.lld to auto-include picolibc.ld from the sysroot’s multilib directory. This linker script contains ENTRY(_start) and references crt0.o directly. The FSP already provides Reset_Handler as the entry point via startup.c and its own linker script (fsp_gen.lld), making picolibc.ld and crt0.o both redundant and conflicting.

This project’s fix: --sysroot is present in c_args (needed at compile time for headers such as setjmp.h, string.h) but is omitted from c_link_args. The linker instead receives -Wl,-L<multilib_lib_dir> pointing directly at the correct ATfE multilib directory (armv8m.main_hard_fp_unaligned_size/lib) so libc.a and libclang_rt.builtins.a can be found without triggering picolibc.ld auto-inclusion. A weak _start stub in src/crt0_stub.c satisfies any residual reference from libc.a.

7. RASC headless invocation: standalone rasc.exe required

e2studio reference project: Code generation is performed interactively inside e2studio’s GUI.

This project’s requirement: Headless code generation via --generate is only supported by the standalone RASC installer (setup_fsp_v6_5_0_rasc_v2026-04.2.exe). The e2studioc.exe bundled with e2studio enters an interactive Eclipse socket wait mode when given --generate and cannot run headlessly. The two executables accept the same command-line arguments but behave differently.

8. configuration.xml must be migrated to FSP v6.5.0 before headless builds

RASC v6.5.0 will generate content for a v6.4.0 configuration.xml but exits with a non-zero code and may produce incomplete output. The fix is to open each board’s configuration.xml in the RASC v6.5.0 GUI, accept the migration prompt, click Generate Project Content, and save. The migrated files checked in to firmware/ra4e2-fpb/configuration.xml and firmware/ra6e2-fpb/configuration.xml were produced this way.
